## Context

客户提供的开关图需要由助手分析为建议点位，再交给用户在工作台调整、确认和出图。原工作台仅有一张图片和浏览器内保存的点位；图像留白会导致画布坐标与导出坐标不一致。多楼层、场景和方案修改需要稳定标识与版本依据。

## Decision

- 一个项目方案包含多幅楼层底图、平铺的点位和引用点位 ID 的场景。每个点位归属一个底图，坐标固定为原图范围的 0–100 百分比。缩放和平移仅改变视图；拖动和导出使用同一坐标基准。
- 助手交付带格式版本的 JSON 点位草稿。工作台先校验和预览，再导入。重复 ID 保留用户已有微调；跨图纸身份冲突拒绝导入。新建议保持待审核状态，不接受草稿文件替用户确认。
- 草稿作为经过类型校验的 JSONB 项目文档保存，并使用 revision 乐观锁。楼层、控制对象和场景在一次写入中保持引用一致，避免导入过程部分成功。
- 确认操作保存独立、不可变的完整快照。后续编辑只改变当前草稿。服务端检查人工确认状态和定位条件，避免仅靠界面保证确认语义。
- 出图从用户最后确认或正在查看的方案数据计算。图上显示点位编号，图外列出控制灯组及关联场景，未确认内容有明确状态标识。
- 点位来源报价保留项目与点位 ID 来源。同步替换该项目已有的点位来源条目，保留手动来源条目；产品数量来自已确认的实体点位，不来自灯光连线或场景数量。

## Consequences

文档存储让导入、保存和导出使用相同结构，也便于历史快照复现。数据库暂不逐行检索每个点位；若未来需要跨项目分析或逐点施工任务，可建立索引或独立投影，而不改变确认快照的历史语义。助手分析仍在本聊天中进行，工作台接收建议文件；首版无需额外的付费视觉服务。
