# easy-floorplan 可借鉴清单

> 对象：https://github.com/nicosandller/easy-floorplan（MIT 协议）
> 目的：只借用「点位图底层交互」适合我们的部分，不引入它的业务逻辑。
> 结论日期：2026-10-22

---

## 一句话结论

**它是一台「画户型」的机器，不是一台「在 CAD 底图上布点」的机器。**
组件本体搬不过来（Lit + 607 处 Home Assistant 依赖），但它的**交互骨架**和**几个具体算法**值得抄，尤其是「撤销/重做」和「同一处点选优先级」——这两样我们目前完全没有。

---

## 我实际试过什么

它自带一套不依赖 Home Assistant 的本地预览页，已经跑起来：

- 地址：`http://localhost:5180/docker/editor-preview.html`
- 跑法：克隆仓库 → `npm ci` → `npx vite --port 5180`（约 2 分钟）
- 预览页自带示例户型，可以拖、可以选、可以改，改动只留在页面里

左侧工具：选择 / 墙 / 门 / 通道 / 窗 / 天窗 / 追踪 / 区域 / 屋顶。
**没有「放设备点位」这个工具**——它的设备图标是绑 Home Assistant 实体（`light.living`、温度针）的，不是自由放置的点。

## 二、能借的（按价值排序）

| # | 能借什么 | 它的做法 | 对我们的价值 | 改造量 |
|---|---|---|---|---|
| 1 | **撤销 / 重做** | 快照栈：每次改动前 `structuredClone` 整份配置压进数组，上限若干步；撤销就弹出、重做就压回 | 我们现在**完全没有撤销**。「布点」是高频操作，误拖一个点就找不回来，这是体验上最大的缺口 | 约 60 行，半天 |
| 2 | **同一处点选的优先级** | `elementsAtPoint()` 返回**按固定优先级排好的候选列表**，在同一个位置重复点击就依次往下选 | 我们现在的做法是「相邻点先并成一个数字角标，点开再选」。它的做法在点位密集时更顺——不用弹小窗，连点两下就换到下面那个 | 约 80 行，半天 |
| 3 | **框选多个** | `elementsInRect()`：只判断每个元素的**代表点**是否落在框内（不是整个包含），逐个元素类型分别收集 | 我们现在只能一个一个点。批量改房间、批量换图标时很需要 | 约 150 行（含批量拖动），1 天 |
| 4 | **选中即改的右侧属性面板** | 左工具栏 → 中画布 → 右属性面板。选中什么，右边就出什么，不弹窗 | 我们现在是**全屏弹窗**，一点开就看不见图纸了。这是最直观的体验差距 | 约 300–400 行，1–2 天 |
| 5 | **命中容差常数** | `HIT = { wall: 11, pad: 4 }`：墙的点击判定是 11 像素，小图标再加 4 像素内边距 | 我们的规范是图标 32px / 点击范围 44px，但没有定义**重叠时谁优先**。这个常数就是答案的起点 | 并入第 2 项 |
| 6 | **吸附 + 网格提示** | 角落吸附 `ENDPOINT_SNAP = 26`（单位），墙端点吸附 `snapWallEnd()`，状态栏常驻提示「吸附到 20 单位网格」 | 我们是百分比坐标，吸附意义不大。但**状态栏常驻提示**这个做法值得学（告诉用户现在处在什么模式） | 小 |
| 7 | **数据分层** | `types.ts` 里墙 / 门 / 窗 / 房间 / 家具全是结构化对象；渲染、命中测试、编辑三套逻辑分开，命中测试是**纯函数、可单测** | 我们的点位也是结构化的，但交互逻辑全混在一个 3345 行的组件里。这条是「模块化」那一轮的佐证 | 属于重构，不单独算 |

## 三、不能借的（以及为什么）

| 不能借 | 原因 |
|---|---|
| **组件本体** | Lit Web Component，不是 React。硬嵌进 Next.js 只会得到一个空编辑器 |
| **墙体 / 门窗 / 家具 / 屋顶绘制** | 我们的底图来自 CAD，不需要在网页上重新画一遍房子 |
| **设备标记** | 绑死 Home Assistant 实体（`hass` 对象）。和我们的「点位 → 产品件数 → 报价行 → 固定交付版本」完全不同 |
| **3D / 投影 / 环境光** | `projection.ts`、`ambient-daylight-*` 那套是给 3D 预览和日照模拟的，我们不需要 |
| **整条数据通道** | 607 处 `hass` 依赖。它不是库，是一个完整应用，没有可单独引用的「底层框架」 |

## 四、核实过的技术事实

| 项目 | 实际情况 |
|---|---|
| 技术栈 | Lit 3.x（Web Component），TypeScript |
| 源码规模 | 7 万行 / 137 个 TS 文件（`editor.ts` 9098 行、`render.ts` 7171 行、`floorplan-card.ts` 3747 行） |
| 与 Home Assistant 耦合 | `hass` 出现 **607** 次；依赖 `custom-card-helpers` |
| 渲染方式 | SVG 与 Canvas 混用（31 个文件出现 svg，38 个出现 canvas） |
| 协议 | **MIT**（可商用、可修改、需保留版权声明） |
| 可移植的纯逻辑 | `src/editor-geometry.ts`（916 行）——但**不是独立模块**，它 import 了 `./render` 和 `./types`。算法可以照抄，代码不能直接 import |
| 更新活跃度 | 仓库很新（2026-10 仍在合并 PR），但同时也意味着接口还在变 |

## 五、建议的落地顺序

如果决定动手，按「风险从低到高」做，每一步都能单独验收：

1. **撤销/重做**（半天）
   最高性价比，用户立刻能感觉到。先只覆盖点位的新增/删除/拖动/改属性。

2. **同一处点选的优先级**（半天）
   解决「两个点叠在一起，下面的那个永远选不到」的问题。先用固定优先级列表，不必上弹窗。

3. **框选 + 批量改**（1 天）
   批量改房间、批量换图标。这是现在完全没有的能力。

4. **右侧属性面板替代全屏弹窗**（1–2 天）
   这一步改动最大，但正是「编辑点位时看不见图纸」的根治办法。
   做完之后，工作台的形态才真正像它那样：左工具、中画布、右属性。

**不建议做的事**：把 easy-floorplan 整个搬进来、或者为了「用它的框架」去重写业务逻辑。它的业务模型和我们的不是一回事。

---

## 六、要不要上 Konva

如果第 3、4 步做得下去，再考虑把画布层换成 [Konva](https://konvajs.org/) / react-konva：

- **能省掉的**：缩放、平移、拖拽、图层、性能优化（点位多到一两千个时才明显）
- **省不掉的**：命中优先级、相邻点分组、点位与产品的联动——这些仍然要自己写
- **要注意**：引入 Konva 会带一套新的坐标体系，和现有的 CAD 百分比坐标换算要划清边界

**结论**：点位少于几百个、交互就是「放点 + 拖动 + 选中」的话，现在 Canvas/DOM 的实现够用，不必为了 Konva 而 Konva。等要加「多选、对齐辅助线、旋转」时再上。
