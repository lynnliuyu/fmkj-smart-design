# 产品库与点位映射整理方案

2026-10-15 补充：[ADR 0006](adr/0006-project-quotation-defaults-and-linked-deletion.md) 允许默认型号直接作未核验客户报价，并固定项目换型和删报价联动点位的语义。本文严格规格 / 价格 / 用料条件继续用于正式采购，不作为阻止所有客户报价的统一条件。对应实现与验收见 Plan 021。

日期：2026-10-14。本文是已实现的选型合同及产品整理流程。结构化产品、点位要求、配套用料与报价校验已通过隔离验收；实际厂商规格和价格仍需逐条核实。实现位置、验证证据与剩余工作见 [Plan 020](../plans/020-product-point-mapping.md)。目标环境是否已应用，以迁移账本和产品整理变更集为准。

## 结论

现有产品大类可以继续使用，但不足以支持精确选型。产品记录需要区分系列和具体规格，点位需要独立表达设备类型与选型要求。图标用于显示，产品 ID 用于关联，具体 SKU 与参数用于决定能否匹配。

仅重新命名产品或调整大类无法保证兼容性。程序现已用设备类型及结构化参数替代原先两套关键词关联规则；名称和图标继续用于查找与展示，选型结论由共用兼容判定得出。

## 整理前的基线

- `products` 有 ID、名称、品牌、平台、大类、唯一 SKU、单位、价格、成本、库存、描述、标签和渠道；缺少结构化设备类型、规格和映射审核信息。`channels` 是来源/销售渠道，不是开关路数。
- 产品大类有 12 个，点位图标有 38 个。一个大类包含多种设备，不能直接一对一关联。
- 点位使用稳定的 `id`，持有 `iconId` 和单个 `productId`。同一个产品可以被多个点位引用；编号和图标不应作为产品身份键。
- `mapProductToPointIcon` 按名称、整段规格描述及大类中的关键词顺序匹配，未命中则使用大类默认图标。
- `findBestProduct` 在名称、规格、标签中任意命中一个图标关键词就返回第一条产品；关联产品下拉框允许选择全部产品。
- 点位报价按“已定位＋已确认＋关联可用产品”计数，一个实体点位贡献一件产品。当前没有规格兼容检查，也没有配件和按米计量的展开。
- 数据审核状态 `active/approved` 表示产品在售/目录审核，不等于选型参数已核实。点位 `confirmed` 表示设计复核，也不等于关联产品兼容。

上述内容记录本次规划的旧版基线。当前实现以 `lib/device-types.ts`、`lib/product-selection.ts`、`lib/point-map-selection-service.ts`、`lib/point-map-procurement.ts` 与本文字段合同为准。

仓库原有账号/组织/订阅及产品目录审核规则继续适用；本合同新增独立的参数核验与价格核验。

## 领域模型

产品大类、设备类型、产品系列、SKU、设备能力、点位要求、图标、选型核验、选用状态和配套用料以根目录 [CONTEXT.md](../CONTEXT.md) 为统一词汇来源。

物理按键数、继电器路数、灯组数和场景数分别记录，不能互相推导。一块三键面板未必有三路继电器；一台兼具 AC 与 PoE 交换功能的设备仍是一台实物。

## 已实施的数据演进

保留 `products.id`、`sku` 和已有业务表，点位继续使用 JSONB 方案文档。

| 位置 | 已实施内容 | 约束 |
| --- | --- | --- |
| 设备类型字典 | 稳定 ID、名称、默认大类、默认图标、允许的参数及图标 | 产品与点位共用；参数由类型校验 |
| 产品 | `device_type_id`、系列关联、系列/具体规格标识 | 系列记录不作为精确选型的可采购 SKU |
| 产品 | 经类型校验的 `specs` | 未知值保留为空，不能默认为 1 键或零火 |
| 产品 | 协议、设备能力、选型核验状态与证据 | 平台、协议和能力分开；米家不等于 BLE Mesh |
| 点位 JSONB | `deviceTypeId`、`requirements` | 可以先定位置和要求，产品暂空 |
| 点位 JSONB | 保留 `iconId`、`productId` | 旧方案兼容；更换要求/型号后重新检查兼容性 |
| 点位配套项 | `materials` 用料清单 | 主产品之外的轨道、配件与服务有独立身份、数量、单位及套装已含标记 |

独立的渠道价格历史表尚未实现。当前保留已有 price/cost 与 channels，通过 `pricing_status`、`pricing_evidence` 表示当前价格的核验情况；多规格或多渠道价格文本仍需人工整理，不能直接成为某个 SKU 的已核价格。

`specs` 不是任意标签袋：按设备类型定义字段、类型和允许值；只校验相关字段。当前保留现有单平台字段，后续有多生态需求时再扩展，不混进协议字段。

历史确认版本继续保持不可变，沿用 ADR 0001。旧单开占位图标不直接推断单键要求。新确认版本保存服务端生成的选型摘要及固定版本图例，产品库后续修改不会改写历史图纸含义。

## 字段合同

下表由增量迁移及业务代码实现。数据库列使用 snake_case，API 对象属性和点位文档使用对应 camelCase；specs 与 requirements 内的参数字典键统一使用下文的 snake_case，不在各入口重新命名。

| 对象 | 字段 | 规则 |
| --- | --- | --- |
| `device_types` | `id text`、名称、大类、默认/允许图标、参数定义版本与 `spec_schema jsonb` | 稳定业务键；字段、类型、单位和允许值集中定义，客户端与服务端复用校验 |
| `products` | `catalog_kind: legacy / series / sku`，默认 `legacy` | 旧产品保留；只有明确的 `sku` 可通过精确选型；不把现有 49 条全部默认转成 SKU |
| `products` | `device_type_id`、`parent_product_id` | 具体 SKU 可关联系列记录；系列同样保留在 products 中以保留旧 ID，不额外建立重复的系列资料表；父项必须为 series，禁止自引用及循环 |
| `products` | `manufacturer_model`、`specs jsonb` | 导入编号继续保留在 sku 中，厂商型号另存；未知规格为空；由设备类型定义相关参数 |
| `products` | `protocols`、`capabilities` | 规范枚举集合；保留现有 platform 表达生态平台；渠道继续使用现有 channels |
| `products` | `selection_status: pending / verified / conflict`，默认 `pending` | 独立于在售及目录审核；资料互相冲突或缺关键字段时不能标 verified |
| `products` | `pricing_status` 与价格核验依据 | 与参数核验分开；原 price/cost 数值继续保留，默认 0 不代表已核零价；正式采购金额需明确价格来源或人工确认 |
| `products` | `selection_evidence`、`selection_reviewed_by/at`、`mapping_revision` | 证据包含来源及适用字段；选型关键属性变化后增加 revision 并重新核验 |
| 点位 JSONB | `deviceTypeId`、`requirements`、`usage: proposed / selected / reserve` | 可以保存未选型的布局；proposed/ reserve 不成为采购数量；结构化参数与自由备注分开 |
| 点位 JSONB | `selection`、保留原 `productId` | 每点位一个主设备，selection 保存选择时的产品 ID、mappingRevision、规格摘要及审核信息；productId 与 selection 的 ID 一致，由服务端检查 |
| 点位 JSONB | `materials` | 用料的稳定 ID、产品、角色、实际数量、单位、必配/已含标记、可选的实体身份及服务端选型快照 |
| 新确认版本 | 选型与图例快照 | 由服务端读取产品和兼容规则生成，不接受客户端伪造“已核验”；原历史版本不补写 |
| `quote_items` | 版本化 `product_snapshot`、`point_map_revision` | 保存显示名称、SKU、规格、单位、类别、图示及来源版本；旧行在产品整理前按当时实际显示结果补迁移前展示快照，独立标记 legacy 来源及采集时间 |

参数定义以 `lib/device-types.ts` 为准：开关包括 `button_count`、`relay_count`、`wiring`、安装与负载；中控屏包括 `screen_size_in`、供电与负载；网络、摄像头和窗帘按各自类型定义角色、供电、安装或供货范围。产品必填字段与点位必须明确的安装条件分别定义，只有适用于该类型的字段才进入必填清单。图纸没有的信息继续留空待核。

类型字典为每个关键参数定义比较方式，例如按键数精确相等、输出能力满足需求、屏幕尺寸在允许范围内。缺失或 null 均表示未知，不使用 0、空字符串或“待核”文字代替数值参数；持久化统一归一为缺失键。未知值不能当作满足条件；兼容结果为 `compatible / incomplete / incompatible`，附缺项或冲突原因。结果每次由规则和当前数据计算，不能只相信文档中保存的 verified 字样。

产品 API、产品库、QuoteDraftProduct、报价选择、点位队列及工作台转换都要保留同一份结构化选型字段。点位找产品、产品/报价生成点位使用同一套判定，不各自重建关键词规则。按米计量或配件产品可加入报价，但不能按四舍五入数量生成同等数量的实体点位。

用户在现有替换入口选择单/双/三/四键或四寸屏，属于设备意图变化，继续解除原关联并重新核验。颜色、图形样式或图例版本的纯显示更新保留产品关联；程序必须区分这两种操作。

### 版本与兼容

- 工作台新方案文档使用 `schemaVersion: 3`，读取旧单图及 v2 文档时作纯内存升级；原文件、数据库行和确认快照保持原样，用户保存草稿时才落库。
- 助手交换草稿升级为 `version: 2`，支持设备要求及选用状态；继续接受旧 `version: 1`。未知未来版本明确拒绝；两种版本号分别管理。
- 旧点位保留全部 ID、编号、坐标、楼层、图标、备注、场景与 productId。设备类型和具体参数可给出候选，但未经复核的旧单开占位图标不能被当作已核单键参数。
- 旧点位没有选用状态时升级为 proposed，并列出需确认项；已有报价继续显示，新的同步先比较变更，不静默删除原条目。
- CAD 坐标交换协议继续为 v1，回传只改位置，保留全部新选型字段；不把产品资料写回客户 CAD。所有读写允许字段清单、导入导出和备份都需覆盖新增字段，避免往返丢失。
- 布局可以在产品待选型时独立确认，沿用现有定位和设计复核条件；正式采购校验另行执行。已确认版本中的旧选型不因当前商品资料变化而重写。

### 旧产品整理与变更集

- 旧产品有明确单一规格且依据充分时，可保留原 ID 并补齐 SKU 属性；混合规格记录保留原 ID，转为系列或 legacy，具体规格建立子记录。
- 不根据型号后缀、渠道价列表或所有可能组合自动生成 SKU；只建立已证实存在的供货规格。颜色等订单属性需要明确，但同价不代表完全兼容，也不代表一定需要拆独立 SKU。
- 整理工具默认只生成 dry-run 变更集，列出旧值、新值、依据、受影响点位和报价。应用以产品 ID 和预期 updated_at / mapping_revision 检查并发变化，并记录操作日志；冲突时重新生成差异。
- 产品整理不自动替换既有点位 productId，不改既有报价名称、规格、单价、折扣、数量或成本。旧记录继续可读，历史引用不删除；重新选型明确绑定新的具体规格。
- 现有报价类别、图片以及部分缺失规格依赖实时 products 回退。先在隔离库实现快照读取，并在产品资料改变前冻结受影响旧报价的实际展示结果；已存在的报价快照和金额原值保持。新增的 legacy 展示快照只证明整理前可见信息，不能声称还原报价最初签发时的资料。
- 整理过程先在隔离数据库演练。厂商资料缺失的条目保持 pending，不因整理工具运行成功而变为 verified。

## 设备类型与图标对照规则

| 点位/设备 | 建议设备类型 | 决定匹配的主要字段 | 图标策略 |
| --- | --- | --- | --- |
| 一至四键开关 | `wall-switch` | 按键数、继电器路数、接线方式、安装尺寸、负载、协议/平台 | 由已确定按键数选择 `switch-1/2/3/4`；未知时标待选型 |
| 场景面板 | `scene-panel` 或已核能力的 `keyed-control-panel` | 按键数、场景能力、是否有负载输出、供电 | `scene-switch`；不能因为有多键就认作多路负载开关 |
| 调光旋钮/控制器 | `dimmer-controller` | 调光方式、负载输出、兼容灯具/驱动、供电 | `dimmer-switch`，通断开关不能代替调光器 |
| 四寸/大屏中控 | `touch-control-panel` | 屏幕尺寸、安装方式、供电、负载路数、网关能力 | 四寸用 `panel-small`；大屏用 `panel-large`；不从“支持空调”推成温控器 |
| 网关 | `smart-home-gateway` | 子设备协议、接入/容量、平台 | `gateway`；屏幕与网关角色分别核对 |
| 摄像头 | `camera` | 室内/室外、供电、联网方式、镜头/视场、存储方案 | `camera`；本客户只考虑室外，具体覆盖待核 |
| AP、路由器 | `wireless-ap`、`router` | 安装方式、制式、供电、AC 管理兼容 | 现阶段共用 `ap` 图形，设备类型必须区分 |
| 无线 AC | `wlan-controller` | 管理能力/数量、AP 兼容型号 | `network-controller`；与暖通空调分开 |
| PoE 交换机 | `network-switch` | 端口数、PoE 标准/预算、上联、集成能力 | `poe-switch`；支持 PoE 供电的摄像头仍是摄像头 |
| 窗帘 | `curtain-motor`、`curtain-track`、`curtain-kit` | 成套范围、电机数量、轨道类型/长度、配件、供电 | 一个轨道＋电机安装点可共用 `curtain`，报价展开用料 |
| 门锁、门磁 | `door-lock`、`contact-sensor` | 锁体/门型，或传感用途及协议 | 当前 `door` 混称“门锁/门磁”，后续拆开图例和类型 |
| 人体、存在探测 | `motion-sensor`、`presence-sensor` | 检测方式、供电、范围、平台 | 当前可共用 `sensor`，类型应区分 |
| 温湿度、烟雾、水浸 | 相应传感器类型 | 检测用途、供电、协议 | 对应现有专用图标 |
| 筒灯、射灯、磁吸灯 | `downlight`、`spotlight`、`track-light` | 功率、开孔、色温/调光、轨道/驱动兼容 | 对应专用图标；不能全部回退成筒灯 |
| 电源、平板灯、格栅灯、风扇灯 | 对应独立类型 | 功率/电压、头数、安装、调光 | 需补图标或明确临时符号，不能借筒灯暗示精确类型 |
| 插座、USB 插座、地插、轨道插座 | 对应独立类型 | 供电、负载、接口/模块、长度 | 使用对应图标；轨道插座暂缺专用图标 |
| 音箱、扬声器 | `smart-speaker`、`ceiling-speaker` 等 | 有源/无源、功放系统、协议 | 现有 `speaker` 只能作概略符号 |
| 网口、电视、配电箱、晾衣架等 | 对应设备或基础设施类型 | 实际供货范围、安装要求 | 使用现有图标；预留接口不自动认定为可采购设备 |

图标不必与设备类型一对一：多种设备可共用概略图形，一个类型也可按规格使用不同图形。图标替换组只是编辑便利，不是电气兼容证明；单键开关与四寸屏之间仍需核接线、负载、盒深等条件。

## 匹配与报价流程

1. 识图先得到点位位置、设备角色、控制意图和不确定事项。未看清键数的开关可保留占位图标，但要求中的键数为空。
2. 用户确定设备类型与要求；系统先过滤停用产品、系列记录、类型冲突和已知参数不兼容的产品。
3. 参数未知的候选进入“待核对”，不视作兼容。不从任意描述、价格备注或所有标签中自动找第一条并绑定。
4. 在兼容候选内按系列、材质、配色、价格等筛选，用户确认具体 SKU 后绑定产品 ID。
5. 更换图标、类型、关键要求或产品时重新检查；客户端和服务端都使用同一兼容检查，旧关联出问题时明确提示。
6. 只把已确认、已定位、型号有效且核验通过的实体设备同步报价；键数不乘采购数量。
7. 配套清单按规则展开，缺少轨道米数或配件选型时提示缺项，不把一个点位直接当一米轨道或一套完整材料。
8. AC/路由/PoE 一体机按物理设备只计一次；预留 AP 点与正式选用点需要区分，候选位置数量不直接成为采购数量。

无合格候选时显示“库内缺产品/参数待补”，允许继续布点。历史图例、点位 ID、坐标与引用保持稳定。

### 报价同步与历史数据

- 草稿保存允许选型不完整，并返回明确诊断；已知不兼容的关联保留为待处理问题，不能伪装成已选型。新确认的 selection 及正式采购同步由服务端重新校验产品状态、具体规格、revision 和兼容条件。
- 正式选用且满足条件的实体点贡献 1 件主设备；用料按独立数量与单位展开。产品系列、待评估、预留、缺资料或冲突项均不直接生成采购数量。
- 同步先生成增加、变化、移除与缺项预览。正式选用点有阻断缺项时不自动覆盖已有点位来源报价。不得把“过滤后为空”当作可以清空旧报价的理由；用户处理问题或明确调整选用范围后再重新同步。
- 服务端报价保存校验点位来源、项目访问权及来源版本，不能相信客户端发来的点位计数/产品绑定；保留手动报价条目和现有权限规则。报价的人工单价、折扣和成本改动不被产品清洗自动覆盖。
- 现有 quote_items 已保存的名称、单位、价格和规格文字继续保持；缺少的展示字段在整理产品前按上一节补 legacy 展示快照，读取优先使用已冻结信息。无法找回的历史信息标为 legacy/未知，不猜测恢复。新数据补 SKU、类型、结构化规格及来源 revision 快照，不通过实时产品表重算历史规格或金额。
- 配套用料已接通：配件和米数分别有产品、角色、数量与单位；未实测的数量为 null。套装已包含部件不重复计费，窗帘电机缺轨道清单或必配项待定会阻断同步。相同实体设备多能力通过显式 `physicalDeviceId` 去重；同 SKU 的不同安装点仍分别计数。

## 实施顺序与验收

1. **先修匹配底线**：新建 AP 不再因 `APP` 字样关联开关；各键数不再按通用“开关”词选中同一个系列；四寸屏不因“面板”命中普通开关。关联下拉先呈现兼容结果，冲突与未知明确标识。
2. **整理现有产品**：保留旧 ID 和资料，补设备类型；把混合键数、接线及其他影响选型的规格标成系列并建立具体规格。只拆实际存在且核实的规格，不盲目生成全部组合。补充本项目缺少的网络与室外监控产品。
3. **接通统一校验**：产品管理、批量导入、点位编辑、产品加入点位、保存和报价同步都读取同一套字典及参数校验。人工选型和自动候选一致。
4. **完成首期报价闭环**：补来源版本、采购校验及新增确认版本的型号/规格/图例快照；旧报价展示保护在产品清洗前完成，不延后到配套功能。
5. **核对组合用料**：在已接通的配套清单中选择实际型号，填实测数量，核对单位及套装已含范围。

重点验收例：

- AP 与描述带 `APP` 的开关不会关联；无线 AC 不落到暖通。
- 描述列出 1/2/3/4 键渠道价格时不能判成四键。键数未知时不默认单键。
- C2 支持控制空调，不会改变其设备类型；智能屏不会默认认定为网关。
- 三键实体面板的采购数量仍为 1；场景键不增加继电器路数。
- 窗帘电机、轨道及传动头不漏项；没有长度时不生成轨道数量。
- 当前正式方案中不兼容的旧关联能被发现，但不会在后台被静默改成另一款产品。
- 参数未知、映射冲突或未选用的候选点位不能自动进入正式采购清单。
