# 030 点位草稿保存：单人单机的简化收口

Status: IN PROGRESS
Date: 2026-10-21
Depends on: 016（API 契约）、021（保存 / 交付收口）、027（本机存储）

> 本计划最初按「多人协作」写，包含服务端变基、字段级合并、离线队列。
> 2026-10-21 用户确认使用者为**单人单机**，这些复杂方案已全部砍掉。
> 判断依据：不存在「覆盖他人工作」的风险，冲突只可能来自用户自己的并发操作。

## 已确认的前提

- **单人单机**：冲突来源只有三种，都是你自己造成的——
  1. 报价页删行 / 改房间联动改了云端点位，而工作台是更早打开的；
  2. 同一个项目开了两个标签页，两边都改了；
  3. 工作台页面放了很久，中间云端被别的页面推进过。
- 因此「用本机稿覆盖云端」最坏只是把**你自己较旧的一版**换成本机较新的一版，不会毁掉别人的工作。
- 数据库草稿仍是唯一权威，本机 IndexedDB 是工作副本；「保存草稿」= 把工作副本发布到数据库。
- 「云端」在本地设备版落地前就是这台机器上的 PostgreSQL（ADR 0010、Plan 028）。

## 目标

1. 冲突不再是死胡同：给出一个显式的「以本机为准保存」，并把被替换掉的云端稿自动留成本机备份。
2. 保存失败必须说清原因和下一步，不能静默返回。
3. 不为单人单机不需要的场景增加机制。

## 非目标（明确砍掉，避免以后又被提出来）

- 不做服务端变基 / 字段级差异合并。单人场景没有要保护的第三方改动。
- 不做离线 outbox 队列。数据库就在本机（或本机局域网），留给 Plan 028 按部署形态再评估。
- 不做「保存结果未知」态的自动回读自愈。有了覆盖按钮，代价从「卡死」降为「点一次」。
- 不改「点『保存草稿』才写数据库」。改成自动保存是另一个决定，会反转 CONTEXT.md:3 与 ADR 0007，
  本轮不动。
- 不改 ADR 0006 的三条用户决定（未核验默认型号报价、换型只影响本项目、删来源行联动删点场景）。

## 不得反转的基线

| 契约 | 依据 |
| --- | --- |
| 草稿 = JSONB + `revision` 乐观锁；确认 = 不可变快照；不匹配 409 | ADR 0001:14、plans/016:42 |
| GET 只要 `point_map.use`；PUT 还要 `project.edit` + 可写成员 | plans/016:42 |
| 数据库草稿权威，IndexedDB 只是副本，不能替代数据库和 JSON 备份 | ADR 0009:14 |
| 保存成功 → 按已保存 revision 刷新**本机报价预览**（空快照也发布）；数据库报价在报价页保存 | ADR 0007:15、plans/021:76、plans/026 |
| 保存期间的新编辑保留 | ADR 0007:18、AI_RUNBOOK |
| 不**静默**覆盖：覆盖必须是用户显式动作，且被覆盖的一版可找回 | docs/point-map-design-workflow.md:28 |

## 阶段

### 030.1 显式覆盖（已实现，待真实数据库验收）

做法（已落地）：
- 冲突状态下显示按钮「以本机为准保存」，点击后二次确认。
- 核心逻辑在 `lib/point-map-draft-override.ts`：先 `read()` 取回云端当前稿与 revision，
  把被替换的那一版交给 `backup()`，再用**刚读到的 revision** 作为基准 `save()`。
  因此覆盖不绕过乐观锁——云端在点按钮的瞬间又被改过时，写入以 409 失败并回到冲突态，绝不自动重试。
- 工作台侧把云端稿写入本机备份槽（`fmkj:point-map:backup:<projectId>`），可从「导出本机备份」取回。
- 用于正常保存的 `cloudRevision` 与覆盖用的基准 revision 完全分开，所以正常「保存草稿」永远不会偷偷覆盖。
- 备份失败不回滚覆盖，但提示里明确说明这一版只在当前页面保留。

验收（已完成）：
- 单元测试 `tests/point-map-draft-override.test.ts`（6 条）：以新读到的 revision 为基准、备份的是被替换的云端稿、
  备份失败仍能保存并如实报告、云端无草稿时不编造备份、第二次并发改动以 409 冒泡而不是覆盖。
- 全量 919 测试、typecheck、ESLint、`next build` 通过。

验收（待做，真实数据库）：在真实项目上制造一次冲突（工作台开两个标签页，或先由报价页改点位），
点击覆盖，读回数据库确认 revision 前进且 `plan` 是本机那一版；确认本机备份可导出。

语义变更声明：ADR 0001 / ADR 0007 只写了「不静默覆盖」，没有写「允许显式覆盖」。本条属于新增语义，
已同步 CONTEXT.md 与 `docs/point-map-design-workflow.md`；若要恢复「冲突必须先导出 JSON 再加载云端比较」
的旧口径，回滚这一条即可（删除按钮与 `lib/point-map-draft-override.ts` 调用，保留其余修复）。

### 030.2 失败提示（2026-10-21 已完成）

- 保存失败在顶部卡片常驻显示，不再只在点位编辑弹窗里可见。
- 服务端错误码（404 / 415 / 403 / 版本号用尽 / 体积超限）映射成可执行中文提示，不再统一说成「云端不可用」。
- 409 提示带上云端 revision 并说明本机稿仍然保留。
- 413 列出各楼层底图体积与合计。
- 无版本号（首次读取云端失败）时点保存不再静默返回。
- 本机 IndexedDB 配额失败转成中文可执行提示。
- 修掉两个假冲突：服务端补写的选型核验快照不再算「本机修改」；加载期间的新编辑不再被当成冲突。

### 030.3 会话过期原地恢复（可选，P2）

单人单机下 403 基本不出现（你就是项目创建者），真正会遇到的是 401 会话过期。
现状：401 会把工作台变成只读，只能刷页。规划：会话过期后重新登录能回到原项目并继续保存，本机稿不丢。

### 030.4 体积上传期提示（可选，P2）

单张 30 MB / 整包 32 MB 是 Plan 016 的历史值，与 ADR 0008 的净底长边 3000 px 规范不匹配。
现状：上传原图不压缩，布点完成后保存才 413（本轮已能在提示里指出是哪张底图）。
规划：按 3000 px 规范在上传期给出体积提示。是否允许自动降采样需要单独决定（会改 ADR 0009 的原图指纹语义）。

## 验收口径

按 AI_RUNBOOK 区分四件事，不能用测试通过代替真实验收：

1. 本机预览：IndexedDB 草稿内容。
2. 数据库已保存：真实项目读回的 `revision` 与 `plan` JSONB 字段。
3. 固定版本：确认版快照不可变。
4. 实际导出：客户 PNG / PDF 从固定版本生成。

030.1 的真实验收：在真实项目上制造一次冲突（工作台开两个标签页或先由报价页改点位），
点击覆盖，读回数据库确认 revision 前进且 `plan` 是本机那一版；确认本机备份可导出。
